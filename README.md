# FlyffWeb

Piece 5 milestones 1 and 2 are accepted. Milestone 3 adds nearby/whisper/shout chat, NPC dialogue and vendor buy/sell. Its VM/device acceptance is pending: [talking checkpoint](docs/piece5-m3-checkpoint.md).

Current game controls: WASD moves, arrows rotate the camera, right-drag/swipe uses the reversed camera direction, and Space or the touch Jump button jumps (including while the joystick is held). Browser zoom/default double-click actions are blocked in the game.

A browser client for FlyFF. Node 24+ and npm 11+. Run `npm install` once in this folder.

What is built so far: a converter that turns the game's files into web files, a viewer for them (Piece 1), a gateway with a login lobby (Piece 2), built so that a browser logs in, picks a server and channel, and lists, creates and deletes characters on your real game servers, and entering the world (Piece 3, milestone 1): **Enter** on a character opens the 3D world where the character was saved, with the other players, monsters and NPCs around it, moving by the game's own rules, with name tags, and the player walks with the keys or the on-screen joystick; and (milestone 2) collision as in the Windows client, so buildings, fences and steep slopes stop you, bridges and stairs carry you and the camera stays out of walls, and tap (or click) to walk to a spot; and fighting (Piece 4, milestone 1): a Vagrant selects and attacks monsters with the combo of its level, with damage numbers, hit sparks, critical and miss banners, monsters hitting back, the status window, target bar and task bar in the Windows client's look, dying and the lodestar, levelling up, the Character window with stat points, the weapon in the hand, and the whole game held sideways (landscape); and skills (milestone 2): the skill window to spend skill points, skills on the task bar and in the action slot placed with the mouse or a finger, and using them, with their motions and effects; and (Piece 6, milestone 1) the world map: M or Start → World Map shows the classic V15 map of the continent you stand on, with its nine picture buttons, your arrow, and the monsters and their booty (the converter writes its catalog, `data/worldMap.json`, from the continent outlines and the map scripts); and (milestone 2) the game's music and sound: the title track, each region's track, the death, level-up, NPC and boss tracks, the motions' and the actions' sounds and the button clicks, with Start → Option's BGM and Sound Effect sliders (the converter's audio stage copies the sounds and music, and writes `data/audio.json`); and (milestone 3) one-tap reconnect: when the connection drops on its own, the world freezes behind a box, and Reconnect logs the same account back in to the same channel and character, with the login kept in memory for 5 minutes and nothing replayed; and (Piece 7, milestone 0) the classic NPC dialogue: a tap on an NPC opens the Windows client's menu beside it (or runs its only entry), and Dialog opens the V15 dialogue window with the NPC's picture, the text page by page, the keyword and answer buttons and the quest lists, reading and sending every dialogue message as Neuz does (the converter's UI stage adds the NPC pictures of `Client/Char` and the window's pictures, and `npcs.json` names each NPC's picture); and (milestone 1) quests: Q or Start → Quest Diary opens the V15 quest window with its tabs, tree, filter and detail, the tracker lists up to five ticked quests at the screen's edge, a condition's place shows on the world map, quest progress shows among the messages and in the chat, and the dialogue shows each quest's levels and the yellow paper when it is ready to hand in (the converter writes the quest catalog, `data/quests.json`, from the client's quest files). While in the world, closing the page asks first. The live tests (`npm run test:live`, `npm run test:live:world`) check it against your servers. Guides for you, the owner: [docs/device-testing.md](docs/device-testing.md) (checklists for your phones and tablets), [docs/hosting.md](docs/hosting.md) (putting the client on the internet), [docs/servers-in-a-vm.md](docs/servers-in-a-vm.md) (the game servers and the gateway in a Hyper-V virtual machine, the client on your PC) and [server-patches/README.md](server-patches/README.md) (the changes the C++ servers need).

The converter's texture stage also needs [KTX-Software](https://github.com/KhronosGroup/KTX-Software/releases) 4.3 or newer (`ktx`). It looks for `ktx` in the `KTX_BIN` environment variable, then on the `PATH`, then in `C:\Program Files\KTX-Software\bin\ktx.exe`.

The converter's audio stage also needs [FFmpeg](https://ffmpeg.org/) (`winget install --id Gyan.FFmpeg -e`), for the MP3 copies of the music that Safari before 18.4 needs. It looks for `ffmpeg` in the `FFMPEG_BIN` environment variable, then on the `PATH`, then in `C:\Program Files\ffmpeg\bin\ffmpeg.exe`. Without it the stage still copies the sounds and the Ogg music, and records one failure.

## Layout

npm workspaces: `packages/*`, `tools/*`, `apps/*`. `server-patches/` is not a workspace.

| Folder | What |
| --- | --- |
| `packages/formats` | `@flyffweb/formats`: `BinaryReader`, `FormatError` and the readers for FlyFF binary formats, and for the game scripts in the resource packs (`propMover.txt`, `propItem.txt`, `character.inc`, `PKSetting.inc`, the honour titles, `World.inc`, the string tables and the `#define` headers; and, from Piece 4, `propJob.inc`, `ExpTable.inc`, `textClient.inc`, the job names of `etc.inc`, the picture-sheet `.inc` files and the `.sfx` effects). Every reader names the C++ function it copies. |
| `packages/scene` | `@flyffweb/scene`: the 3D code the viewer and the client share: the asset store and loaders, characters assembled from parts (with their bounding box and the hand and forearm grips a held weapon or shield hangs from), the effects (`effects/`: an `.sfx` effect's keys played as Neuz plays them, drawn with its blending), the world stage (terrain tiles and objects streamed around a point, light, sky and fog), the keyboard, the on-screen joystick and the touch-screen rule they share, and the measurement overlay. |
| `packages/protocol` | `@flyffweb/protocol`: the FlyFF network protocol in TypeScript, for the browser and Node, with no Node-only code. `ar/` is a reader and writer with the layout of the C++ `CAr` class (little-endian numbers, strings as a length plus bytes); `framing/` has CRC32, the frame writer and reader and the protocol-ID packet; `crypto/` has MD5 and AES-128-CBC in plain TypeScript (the password hash and the encrypted password block of CERTIFY; WebCrypto is not available on plain-HTTP pages such as the Wi-Fi test setup); `messages/` has one module per server, `certifier.ts`, `login.ts` and `world.ts`, with that server's packets; `bundle.ts` reads the world server's bundles (JOIN and SNAPSHOT), with their table of contents when the patched world server sends one, and `world/` the messages in them the browser uses (players, monsters and NPCs appearing, moving and leaving; the own character's numbers, skills, inventory and task bar; the fight: attacks, damage, deaths, experience, levels, stats and revival; and skills: using them, skill points, the action slot and their effects); `text.ts` decodes server text as windows-1252. Every module names the C++ function it copies. |
| `packages/testkit` | `@flyffweb/testkit`: `FakeFlyffServer`, a pretend FlyFF server for tests (it announces a protocol ID, checks the frames it receives and answers; the gateway tests run against it), writers that build the servers' packets byte by byte, and `createWorldScript`, a pretend cache and world server for the client's tests (a script can also answer a packet the client sends, for the fight tests), and `newVagrantOwn`, a new character's own data. |
| `tools/capture` | `@flyffweb/capture`: records one Neuz login session, packet by packet, into a test fixture (`npm run capture`). Steps in [tools/capture/README.md](tools/capture/README.md). |
| `tools/convert` | `@flyffweb/convert`: Node converter from the read-only client folder to hashed web assets in `dist/assets`. Settings: `apps/gateway/gateway.config.json` (see "Local settings files"). |
| `apps/client` | `@flyffweb/client`: the real game client, a Vite page. Milestone 2 adds skills (`skills/`: the skill rules and using skills) and the skill window and the task bar's edits (`hud/skillWindow.ts`, `hud/taskBarEdits.ts`, `hud/slotGestures.ts`). The collision shapes stream in with the world's tiles (`packages/scene/src/world/collision.ts`). It reads the converted game files through `/assets/`, as the viewer does. Its end-to-end tests (Playwright) are in `apps/client/e2e`; the live tests against your real servers are `apps/client/test/lobby.live.test.ts` and `world.live.test.ts`. |
| `apps/viewer` | `@flyffweb/viewer`: Vite + Three.js viewer. ## Client folder

Tests that read real game files need the FlyFF client folder. By default it is `../Client` (next to this folder); set `FLYFF_CLIENT` to use another path. It is read-only: nothing here writes into it. Without it, those tests are skipped with "Client/ not found — set FLYFF_CLIENT".

## Running the client on your PC

With the game servers running, `apps/gateway/gateway.config.json` in place and the client converted into `dist/assets` (see "Converting the client"), start these in two windows, in this folder:

```
npm run gateway
npm run dev:client
```

Open http://localhost:5174/ and log in with a test account, then tap **Enter** on a character. Put the new world and cache servers in service first ([server-patches/README.md](server-patches/README.md)). With the old world server the browser still enters the world, but it reads only part of what that server sends, so other players, monsters and NPCs can be missing or stand still (the overlay's `indexed` number then stays at 0); with the old cache server, the servers see every browser player at the gateway's address. For phones and tablets over Wi-Fi, follow the checklists in [docs/device-testing.md](docs/device-testing.md). To put it on the internet, follow [docs/hosting.md](docs/hosting.md).

## Local settings files

Two files stay on your machine: git ignores them. Each is made by copying a committed example, and each is found by its fixed name.

| Your file (not in git) | Copy it from | What it holds |
| --- | --- | --- |
| `apps/gateway/gateway.config.json` | `apps/gateway/gateway.config.example.json` | What `npm run gateway` needs: where the gateway listens (`listen`), which page addresses may connect (`allowedOrigins`, the exact address the browser shows, for example `http://192.168.1.20:5174`), the proxies it trusts (`trustedProxies`), whether it passes the player's address to the certifier (`sendClientAddr`), and the table of servers it may reach (`routes`, keyed by the address the servers advertise). Optional `limits` override the defaults. |
| `apps/client/test/live.config.json` | `apps/client/test/live.config.example.json` | What `npm run test:live` needs: a throwaway test account, its Bank PIN, and a gateway of its own for the test; and, for the world test, a `world` section with two throwaway accounts (the first one's character fights an Aibatt, so it should be new or low level). It holds passwords: never commit it. The `_comment` at the top of the example explains each setting. |

In PowerShell, from this folder:

```
Copy-Item apps\gateway\gateway.config.example.json apps\gateway\gateway.config.json
Copy-Item apps\client\test\live.config.example.json apps\client\test\live.config.json
```

Then open each copy in a text editor and change it as the guides say. The gateway checks its file when it starts and tells you what is wrong with it.

## Converting the client

Converts the whole client folder into web assets in `dist/assets` (git-ignored, and the folder the viewer reads):

```
npm run convert
```

It runs six stages in order: textures (to `.ktx2`), models (`.chr` skeletons, `.ani` motions and `.o3d` models to `.glb`, and each model's collision shape to `collision/<model>.bin`), effects (every `.sfx` the model index names to `effects/<name>.json`, and the textures those effects use, with each frame of a texture animation, to `textures/sfx/<name>.ktx2`), ui (every picture of `Icon/`, the window pieces of `Theme/Default` that the windows use and `SFX/DmgEffect.dds` to `ui/<name>.png`, and every item icon of `Item/` to `ui/item/<name>.png`, each with the colour key made transparent, and the frames of the damage-number and target-corner sheets to `data/uiSheets.json`), worlds (a `manifest.json` per world and one `.bin` tile per `.lnd`), then data (the JSON catalogs `data/movers.json`, `items.json`, `npcs.json`, `nameColors.json`, `honorTitles.json`, `worlds.json` (world id to world folder, from `World.inc`), `itemProps.json`, `jobs.json`, `exp.json`, `texts.json`, `skills.json` and `effectsIndex.json`, built from the game scripts in the resource packs and naming the models, skeletons, motions, effects and icons the earlier stages converted). The client folder is only read. On the real client, textures, models, worlds and data took about 7 minutes and wrote about 975 MiB (16,514 files, 1,144 of them collision shapes, plus `index.json` and `report.json`); effects and ui add about a minute and 14 MiB (5,850 files). [docs/conversion-baseline.md](docs/conversion-baseline.md) has the numbers. The texture and effects stages need `ktx` (see the top of this file); without it each records one failure ("KTX-Software" in `report.json`), converts no texture, and the run exits 1.

Useful options (`npm run convert -- --help` lists all):

```
npm run convert -- --jobs 8                    # files converted in parallel (default: CPU count - 1)
npm run convert -- --only WdMadrigal           # one world; also matches model, texture, effect and picture base names, with * as a wildcard
npm run convert -- --only data                 # just the game-data catalogs (the data stage matches the name "data")
npm run convert -- --only effects,ui,data      # a comma separates globs; the effects and ui stages match their names too
npm run convert -- --client "D:/FlyFF/Client"  # another client folder (or set FLYFF_CLIENT)
npm run convert -- --out "D:/flyff-assets"     # another output folder (never inside the client folder)
```

Write paths with forward slashes (or in quotes): Git Bash drops the backslashes of an unquoted `D:\FlyFF\Client`.

Every output file is named `<name>.<first 10 hex of sha256>.<ext>` and `index.json` maps each logical key (for example `models/part_mvag01upper.glb`) to its hashed path. A partial run (`--only`) merges into the `index.json` already in the output folder, so it does not wipe the rest. Nothing deletes files an earlier run wrote, so to start clean remove `dist/assets` first.

The exit code is 0 when done, 1 when some files failed (unless `--allow-failures`), 2 for a bad command line or an unusable folder.

### Reading `report.json`

`dist/assets/report.json` is written at the end of every run:

| Field | What |
| --- | --- |
| `totals`, `kinds` | `ok`, `warn`, `failed`, `bytesIn` and `bytesOut`, in total and per kind (`textures`, `skeletons`, `motions`, `models`, `worlds`, `data`; `stage` and `index` only appear when something went wrong there). |
| `warnings` | `{ kind, source, message }` for things that are expected and are not failures: files skipped on purpose (models Neuz itself rejects, motions no skeleton fits) and things left out of a file that is still converted (objects with an SFX model, a texture that does not exist). |
| `failures` | A file that could not be converted: `{ kind, source, message }`, and for a damaged file also `file`, `offset`, `unit`, `reader` and `cppRef` (the C++ function the reader copies). A bug in the converter itself has a `stack` instead. |

The console summary prints only counts and ends with `Total: N ok, N warn, N failed`; it does not print failure messages, so always check `failures`:

```
node -p "JSON.parse(require('fs').readFileSync('dist/assets/report.json','utf8')).failures.length"
```

A good run prints `0`. Read the warnings to see what was left out and why; the baseline lists the 166 the first three stages give on the real client. The data stage adds 81 more: movers (mostly pets) with motions or a model the model stage did not convert, which the catalogs leave out. A partial run's `report.json` covers only that run.
