# Redeem codes Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** The owner makes codes in the panel (VIP tier + days, up to 6 game items, or both; Everyone / Only these
accounts / One-use batch; an end time), and players redeem them in an in-game Redeem Code window; items come by
in-game mail and the game moves them into the bag.

**Architecture:** All in FlyffWeb, no game server change. New SQL in `apps/web/sql/vip.sql` (tables + procedures,
installed by `Install-Vip.ps1`). A new `apps/web/src/codes/` module: key text rules, store types, SQL stores, the site
routes `POST /api/codes/check|redeem` (reached through the VIP routes, on the player's site session), and the mail
delivery (panel login, right after a redeem, retried by the 5-minute VIP job). A Codes view in the panel's VIP tab. In
the client: VipApi calls, a session keep-alive, the Redeem Code window (Start → Extras), and a mail taker that moves
`Code reward #<id>` mails into the bag.

**Tech Stack:** TypeScript, Node http, `mssql`, SQL Server T-SQL, vitest, the panel's plain ES modules, the client's
ResWindow HUD, Playwright (owner's runs only).

**Spec:** `docs/superpowers/specs/2026-11-20-vip-codes-design.md`

## Global Constraints

- No change to the World or Database server, no convert, no new pictures to convert.
- Codes work only when web.config.json has both the `vip` and the `admin` sections; otherwise every code route answers
  `503 {error:'off'}` and the window says "Codes are not available right now."
- The site login `flyffweb_site` may use codes and read its own character; only `flyffweb_admin` writes mail.
- Every procedure: typed parameters, no SQL built from text, `SET XACT_ABORT ON` where it writes. Times UTC, as text
  ending in Z.
- Key text: spaces and dashes ignored, letters upper-cased, then `^[A-Z0-9]{4,32}$`. Random keys: 16 characters from
  `ABCDEFGHJKMNPQRSTUVWXYZ23456789` (no 0 O 1 I L), shown as `XXXX-XXXX-XXXX-XXXX`.
- A code gives a VIP (level 1-4, days 1-366), up to 6 item stacks (count 1..the item's stack size), or both; never
  neither. One use per account per code. Everyone cap 1-100,000 or none. One-use batch 1-500 keys. Only-these list
  1-500 existing accounts. End time in the future, at most 366 days ahead.
- VIP rule: none live → the code's tier from now; same tier → days added to its end; lower than live → the whole code
  refused (`lower_vip`); higher than live → only with `confirm: true` (else `confirm`), the old tier ends now.
- Limits: 10 wrong tries an hour per account, 30 per address (`unknown` and `not_listed` count); 30 redeems an hour
  per account.
- Mail: title `Code reward #<use id>`, text `From code "<label>". Collect within 15 days.` (cut to 255), one mail per
  stack, server index 51, `MAIL_STR 'A1'`, once per use (`WEB_CODE_SENT`).
- Never log the code text: log lines are `code <address> <account> <codeId or -> <result>`.
- Plain short English in every message; the window's texts are exactly the spec's table.

## Review Focus

- A redeem answer lost on the way (timeout): the second press with the same request id must get the first answer
  (`repeat: true`), not "You already used this code" — Task 3 and Task 4 tests pin it.
- Two redeems of an Everyone code with cap 1 at once, or of one one-use key by two accounts: one wins, the other gets
  `claimed` / `key_used` — the SQL holds UPDLOCK, HOLDLOCK on the key and the code rows (Task 1 text test); the memory
  store test does them back to back (Task 3).
- A player whose site session ran out (web service restart): the window must ask for the password and then carry on
  with the same code, not lose the typed code — Task 8 test (and Task 9 for the row).
- An item-only code redeemed by a VIP4 player: no VIP check at all, it must work — Task 3 test.
- The game takes a mail item only for its own `Code reward #<id>` mails from sender 0: a player's mail with the same
  title must never be taken — Task 10 test.

  - `WEB_CODE_ACCOUNT (codeId, account varchar(32), PK (codeId, account))`;
  - `WEB_CODE_USE (id IDENTITY PK, codeId, keyId, account varchar(32), requestId varchar(64), idPlayer char(7),
    characterName varchar(32), usedAt, address varchar(45), vipLevel tinyint, vipDays smallint, vipEndsAt NULL,
    replacedLevel tinyint NULL, replacedEndsAt NULL, deliveredAt NULL, deliveredTo char(7) NULL, deliveredName varchar(32) NULL)`,
    UNIQUE `(codeId, account)`, UNIQUE `(account, requestId)`, index `(deliveredAt, id)`.
- Produces (CHARACTER_01_DBF table): `WEB_CODE_SENT (useId PK, idPlayer char(7), characterName varchar(32), sentAt)`.
- Produces (procedures; result codes shared by check and redeem: `1` ok, `2` ok and it replaces a lower VIP (check
  only), `3` repeat (redeem only), `-1` unknown, `-2` expired, `-3` inactive (turned off; never called `off`, which is the service's 503), `-4` claimed (Everyone cap reached), `-5`
  key_used, `-6` mine (this account used the code), `-7` not_listed, `-8` lower_vip, `-9` confirm):
  - `usp_WebCodeCheck @account varchar(32), @key varchar(32)` → recordset 0, one row: `result, codeId, label, vipLevel,
    vipDays, expiresAt, liveLevel, liveEndsAt`; recordset 1: `itemId, count` by slot. No writes, no locks.
  - `usp_WebCodeRedeem @account, @key, @requestId varchar(64), @idPlayer char(7), @characterName varchar(32),
    @address varchar(45), @confirm bit` → recordset 0: `result, useId, codeId, label, vipLevel, vipDays, expiresAt,
    liveLevel, liveEndsAt` (after the redeem: the new VIP; on a refusal: the live one); recordset 1: items.
    Order: repeat (an existing use with this account and request id → `3` and that use's data) → BEGIN TRAN → key row
    `WITH (UPDLOCK, HOLDLOCK)` (`-1`) → code row `WITH (UPDLOCK, HOLDLOCK)` → `-3` inactive → `-2` expired → `-6` mine →
    `-7` (kind L, not listed) → `-5` (kind K, key used) → `-4` (kind E, `uses >= maxUses`) → VIP (`WEB_VIP WITH (UPDLOCK,
    HOLDLOCK)`: live and higher → `-8`; live, lower and `@confirm = 0` → `-9`) → insert the use, `uses + 1`, key
    `usedBy`/`usedAt` (kind K), the VIP as `usp_AdminVipGive` does it with `@days = vipDays` and no gift, with
    `replacedLevel`/`replacedEndsAt` when a lower live tier was replaced, the account letter as Give VIP sets it → COMMIT.
  - `usp_AdminCodeAdd @label, @kind, @vipLevel, @vipDays, @maxUses int NULL, @expiresAt datetime2(0), @admin,
    @item1..@item6 int = 0, @count1..@count6 int = 0, @keys xml, @accounts xml` (`<k>KEY</k>…`, `<a>account</a>…`, read
    with `.nodes()` — no STRING_SPLIT, the old databases' compatibility level may lack it) → one row `result, id,
    detail`: `1` with the id, `-1` a key already exists (detail = that key), `-2` an account does not exist in
    `ACCOUNT_TBL_DETAIL` (detail = that name), `-3` a value out of range. One transaction.
  - `usp_AdminCodeList` → codes newest first: every WEB_CODE column, `keysTotal`, `keysUnused`, `firstKey` (the key of
    an E or L code, NULL for K); recordset 1: all codes' items `codeId, slot, itemId, count`.
  - `usp_AdminCodeGet @id` → the code row, its items, its accounts (3 recordsets).
  - `usp_AdminCodeKeys @id` → `keyText, usedBy, usedAt` by id.
  - `usp_AdminCodeSave @id, @label, @expiresAt, @isOn` → `changed` 1/0.
  - `usp_AdminCodeUses @id, @max` → the uses newest first (every WEB_CODE_USE column but requestId).
  - `usp_AdminCodePending @max, @afterId` → undelivered uses after `@afterId`, oldest first: `id, codeId, label,
    account, idPlayer`; recordset 1: their codes' items. `usp_AdminCodePendingOne @useId` → the same for one use.
  - `usp_AdminCodeMarkDelivered @useId, @idPlayer char(7), @characterName` → `changed` 1/0 (only while undelivered).
  - CHARACTER_01_DBF `usp_WebCodeCharacter @account, @idPlayer char(7)` → `characterName` of that character when it is
    the account's, `serverindex = '01'`, not deleted (`isblock` not 'D'); no row otherwise.
  - CHARACTER_01_DBF `usp_AdminCodeMailSend @useId, @account, @idPlayer, @title varchar(128), @text varchar(255),
    @item1..@item6, @count1..@count6` → `result, idPlayer, characterName`: as `usp_AdminVipGiftSend` but keyed on
    `WEB_CODE_SENT`, and the character is `@idPlayer` when it is still the account's and not deleted, else the gift
    rule (online, then most TotalPlayTime, then lowest id); `0` when the account has none.
  - Grants: the two `usp_WebCode*` of ACCOUNT_DBF to `flyffweb_site`; every `usp_AdminCode*` to `flyffweb_admin`; in
    CHARACTER_01_DBF `usp_WebCodeCharacter` to `flyffweb_site` (a new `IF EXISTS … flyffweb_site` block) and
    `usp_AdminCodeMailSend` to `flyffweb_admin`.

  export interface CodeRouteDeps {

    failsByAccount: HourlyLimit;   // 10 an hour

  - `POST /api/codes/check` `{code}` → `200 {ok: true, offer, vip, replaces}`.

    on a redeem `ok` with `repeat: false`: `redeemsByAccount.add`, then `await deps.deliver(useId)`.
