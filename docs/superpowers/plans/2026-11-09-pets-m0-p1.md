# Pets M0 + P1 Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Read every pet field and pet message the world server sends (M0), and let the player summon and recall pick-up
pets from the bag and task bar (P1).

**Architecture:** M0 is protocol only: a new `packages/protocol/src/world/pets.ts` with the pet data and the 12 pet
messages, the pet kept in `InventoryItem`, another player's pet in `AddedPlayer`, and the own summoned pet's bag slot read
past the three banks of the own ADD_OBJ. The client stores nothing new yet. P1 is one rule in `premiumItems.ts`: an
`IK3_PET` item is used with a plain DOUSEITEM; the server makes the pet mover, which the client already shows and moves
as a peaceful NPC.

**Tech Stack:** TypeScript, Vitest, `@flyffweb/protocol`, `@flyffweb/testkit`, `apps/client`.

**Spec:** `docs/superpowers/specs/2026-11-09-pets-research.md` (sections 2.3, 2.4, 3, 4.2, 8, 9).

## Global Constraints

- Every reader copies one `CDPClient::On*` handler and cites its C++ file:line, as the other readers do.
- Ids: PET_CALL 0x0110, PET_RELEASE 0x0111, PET_LEVELUP 0x0112, PET_SET_EXP 0x0113, PET 0x0114, PET_STATE 0x0115,
  PET_FEED 0x0116, PET_MILL 0x0117, QUE_PETRESURRECTION_RESULT 0x0203, SET_PET_NAME 0x9100, MOVER_CHANGESFX 0x8800,
  VISPET_ACTIVATE 0x8801 (`_Network/MsgHdr.h:1194-1201`, `:1237`, `:1271`, `:1309-1310`).
- `MAX_PET_NAME` 17, `PL_MAX` 6, `MAX_BANK` 42, `NULL_ID` 0xffffffff; `time_t` is 4 bytes (`_USE_32BIT_TIME_T`).
- No server change, no `__BB_*` feature.
- Builders run the quick tests only (`npx vitest run <files>` and `npm run typecheck`).

## Review Focus

1. A pet name of the full 16 bytes: read whole, nothing left over (test in Task 1 and Task 2).
2. An item with a pet, vis keep times and the transform flag together: all three kept (Task 1).
3. Banks that hold items with pets before the own `dwPetId`: the slot is still found (Task 3).
4. Banks that cannot be read (cut short): the inventory is kept, `petSlot` is absent, no throw (Task 3).
5. Another player with no pet (`NULL_ID`) has no `pet` field; with one, `MAKELONG( index, level )` is split (Task 1).
